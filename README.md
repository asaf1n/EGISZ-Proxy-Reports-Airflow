## Контекст: ЕГИСЗ, СЭМД, обмен и где в нём наш контур

**ЕГИСЗ** — единая государственная информационная система в сфере здравоохранения. Для клиники ключевое взаимодействие — передача **СЭМД** (структурированных электронных медицинских документов) в **РЭМД** (реестр электронных медицинских документов).

Между МИС и ЕГИСЗ стоит проксирующий шлюз. Он пишет сообщения в журнальную БД **`proxy_egisz`** (Firebird). Сервис строит на её основе документную витрину для BI и оперативного контроля.

### Схема регистрации СЭМД и что из неё видит журнал

По методическому документу «Описание выполняемых проверок в РЭМД» регистрация состоит из одиннадцати шагов. Модель учитывает два этапа проверки и два ответа: синхронный на приём запроса и асинхронный на результат.

| Шаг | Что происходит | Наблюдаемость в журнале шлюза |
| --- | -------------- | ----------------------------- |
| 1 | МИС вызывает `registerDocument` в РЭМД | Исходящий вызов находится вне `EXCHANGELOG` |
| 2 → 2.1 | Грубая проверка структуры запроса; при отказе — синхронный ответ с ошибкой, сценарий завершён | Синхронный участок вне журнала |
| 3 | Синхронный ответ: запрос принят, регистрация ещё выполняется | Синхронный ответ относится к исходящему вызову |
| 4 | РЭМД запрашивает файл СЭМД (`getDocumentFile`) | Первое наблюдаемое событие документа |
| 5 | МИС передаёт файл в ответе | Фиксируется в журнале |
| 6 → 6.1 | Полная проверка запроса; при отказе — асинхронный ответ с ошибкой | Ответ фиксируется в журнале |
| 7 → 7.1 | Проверка файла; при отказе — асинхронный ответ с ошибкой | Ответ фиксируется в журнале |
| 8 | Асинхронный ответ с подтверждением регистрации и `emdrId` | Ответ фиксируется в журнале |

Из схемы регистрации следуют два правила модели данных:

1. **`getDocumentFile` — запрос файла со стороны РЭМД** (шаг 6). Он выполняется уже *после* того, как запрос прошёл проверки этапа 1. `first_sent_at` фиксирует момент запроса файла РЭМД.
2. **Синхронный ответ находится вне наблюдаемого журнала.** Он относится к исходящему `registerDocument`; `EXCHANGELOG` фиксирует входящий участок обмена. Ветка `'accepted'` в `classify_async_status` зарезервирована на случай журналирования исходящей подачи шлюзом.

### Синхронные отказы при подаче

Документы, отклонённые на шаге 3.1, находятся вне аналитического корпуса: сценарий завершается до запроса файла, а след отказа остаётся в синхронном ответе за пределами `EXCHANGELOG`. Доля успеха и объёмы считаются по наблюдаемому корпусу. Полное покрытие этой зоны требует журналирования исходящих вызовов на стороне шлюза.

## Архитектура и поток данных

Схема **ELT**: Airflow извлекает и загружает; парсинг, нормализация, сборка документа и классификация ошибок — в PostgreSQL (`db/`). Metabase читает представления `rpt_*`.

```
proxy_egisz (EXCHANGELOG, JPERSONS, EGISZ_LICENSES)
        │  extract
        ▼
exchangelog_raw  ──transform──►  transactions  ──►  documents
        │                              │                │
        │                              └──── document_attributes
        ▼
   etl_state (позиции)                dim_* (справочники)
                                        │
                                        ▼
                                   rpt_*  ──►  Metabase
```

| Компонент | Роль |
| --------- | ---- |
| `proxy_egisz` (Firebird) | Журнал обмена и справочники — источник |
| Airflow | Два DAG: приём фактов и обслуживание |
| `dwh_egisz` (PostgreSQL) | Raw, факты, справочники, правила ошибок, `rpt_*` |
| Metabase | Шесть дашбордов, пять моделей поверх `rpt_*` |

Служебные БД Airflow и Metabase отделены от `dwh_egisz`.

## Источник данных

Инкрементальная выборка журнала — keyset-курсором по монотонному `EXCHANGELOG.LOGID`.

| Таблица | Детализация | Поля |
| ------- | ----- | ---- |
| `EXCHANGELOG` | 1 строка = 1 SOAP-сообщение | `LOGID`, `LOGDATE`, `CREATEDATE`, `MSGID`, `LOGSTATE`, `LOGTEXT`, `MSGTEXT`, `URI` |
| `EGISZ_MESSAGES` | 1 строка = 1 подача через IPS | `EGMID`, `MSGID`, `REPLYTO`, `DOCUMENTID`, `CREATEDATE` (момент внесения строки в таблицу прокси) |
| `JPERSONS` | Организация | `JID` (`bigint`), `JNAME`, `JINN`, `FIR_OID` |
| `EGISZ_LICENSES` | Лицензия МО | `mo_uid` (регистрационный OID), `JID`, `MO_DOMEN` (адрес обмена, он же `REPLYTO` подачи) |

`MSGTEXT` — полный SOAP/XML (BLOB в источнике, `text` в DWH). Бизнес-поля извлекаются при transform; исходный журнал остаётся неизменным. `LOGDATE` — служебная метка строки журнала; дата документа берётся из payload (`creationDateTime`). `URI` определяет подсистему ЕГИСЗ: `/emdr/callback` — РЭМД, `/ips/callback` — ИЭМК.

`EGISZ_MESSAGES` — реестр подач IPS: `MSGID` исходящего сообщения, `REPLYTO` endpoint клиники, `DOCUMENTID` localUid для РЭМД. В структуре ИЭМК localUid отсутствует; для endpoint `:9921` `DOCUMENTID` в DWH не переносится в `document_uid`. `registerDocument` и синхронный ответ на него в `EXCHANGELOG` не попадают: клиника получает синхронный ответ сразу от IPS. `EXCHANGELOG` содержит входящие вызовы ЕГИСЗ→шлюз; связь ответа с документом строится через `dim_message_document` (см. §«Связывание сообщений»). Выборка обеих таблиц — keyset-курсором: `EXCHANGELOG` по `LOGID`, `EGISZ_MESSAGES` по `EGMID`.

Глубина приёма ограничена окном по `CREATEDATE` (`EGISZ_EXTRACT_DEPTH_DAYS`, по умолчанию 30 суток). Окно задаёт нижнюю границу отметки, внутри страницы курсор идёт по идентификатору. Отметка ниже окна поднимается к его границе; актуальные отметки сохраняются и растут монотонно (см. deploy/README.md §«Настройки DAG»).

Границу окна ищет `MIN(<id>) WHERE CREATEDATE >= ?` — скан по диапазону дат. Ему предшествует проба даты строки сразу за отметкой (чтение по индексу): для отметки внутри окна скан пропускается. На источнике проба быстрее скана в сотни раз; в установившемся режиме приём выполняет только индексное чтение.

`EGISZ_MESSAGES` принимается по порядку `EGMID` без отбора по `MSGID` и `DOCUMENTID`. Неполные строки хранятся как факт подачи. Пустой `DOCUMENTID` является health-сигналом для РЭМД; для ИЭМК это штатное значение.

## ELT-конвейер

Два DAG: приём фактов и суточное обслуживание. У каждого `max_active_runs = 1`.

### `egisz_etl_dag` — каждые 5 минут

| Задача | Действие |
| ------ | -------- |
| `extract_exchangelog` | `EXCHANGELOG` → `exchangelog_raw` по курсору журнала |
| `extract_registry` | `EGISZ_MESSAGES` → `dim_message_document` по курсору реестра |
| `sync_dictionaries` | `JPERSONS` → `dim_organizations`, `EGISZ_LICENSES` → `dim_licenses`; при изменениях пересчитывает JID документов |
| `transform` | Разбор транзакций в записи по документам |
| `refresh_marts` | Обновление витрин |

### `egisz_maintenance_dag` — раз в сутки

| Задача | Действие |
| ------ | -------- |
| `consistency_check` | Страховочная проверка полноты журнала за последние 7 дней |
| `maintain_partitions` | Месячное партиционирование |

### Как это держится

**Две отметки, по разным объектам.** Выгрузка ведёт свою позицию в журнале шлюза, разбор — свою в raw. Отставание разбора сохраняется только в позиции raw; позиция выгрузки остаётся подтверждённой точкой журнала. Хвост raw выводится из самой таблицы.

**Отметка идёт по непрерывному участку.** Журнал нумеруется подряд, поэтому пропуск в странице означает строку в процессе коммита на источнике. Отметка выгрузки встаёт перед разрывом и переступает его после появления строки; сами строки страницы грузятся целиком. Разбор ограничен отметкой выгрузки: фактами становится подтверждённо вычитанный участок журнала.

**Пересчёт архива — по фактам и словарной привязке клиник.** Батч `transform` пересчитывает реквизиты и версии затронутых документов. При изменении справочников организаций или лицензий DAG резолвит сохранённый `documents.jid` по `documents.org_oid` и host-пути; витрины обновляются в конце цикла.

**Обрыв связи с источником сохраняет локальную обработку.** Задачи, ходящие в шлюз, повторяются дважды с минутной паузой. Последующие шаги используют состояние конвейера, разбирают уже загруженный raw и обновляют витрины.

**Повтор безопасен на обеих фазах.** Загрузка идемпотентна, строка журнала в источнике остаётся неизменной, повторный разбор пропускает уже разобранное. Отметки двигаются только после успеха; следующий запуск продолжает с последней подтверждённой точки. Уникальные ключи защищают от дублей документов.

## Парсинг и нормализация

Каждая строка `exchangelog_raw` парсится **один раз** функцией `parse_exchangelog_row(msgtext, msgid, logtext)`; результат пишется в `transactions` (`xml_*`). Попытка парсинга фиксируется в узкой таблице `exchangelog_parse_attempts` (LOGID). Строки без реквизитов (`msgid`/`localUid`/`emdrId`/`getDocumentFile`) получают маркер попытки и остаются вне `transactions`, поэтому широкое окно проверки полноты обходит их без повторного разбора. Дальнейшая сборка документа читает только `transactions`.

Утилиты (`db/02_functions.sql`):

| Функция | Назначение |
| ------- | ---------- |
| `xml_text` | Текст тега XML без привязки к namespace |
| `normalize_message_id` | `urn:uuid:` → единый формат |
| `message_registry_key` | Канонический ключ реестра подач: без дефисов, без префикса, в верхнем регистре |
| `dwh_id` | Ключ **экземпляра/версии** документа: `lower(localUid)` (см. §«Версии и идентичность документа») |
| `egisz_subsystem` | Подсистема ЕГИСЗ (РЭМД/ИЭМК) по `URI` вызова |
| `resolve_document_jid` | JID: `org_oid` из XML → `dim_organizations.fir_oid`; fallback по host/gost-endpoint |
| `normalize_semd_code` | Код СЭМД из payload |
| `classify_async_status` | Статус сообщения до уровня документа |

Извлекаемые поля:

| Поле | Источник | Правило |
| ---- | -------- | ------- |
| `msgid` | `<messageId>` / `MSGID` | Собственный MSGID текущего сообщения |
| `relates_to_msgid` | `<relatesToMessage>` / `<relatesTo>` | Связанный MSGID из XML; используется для поиска подачи в `dim_message_document` |
| Локальный ID РЭМД | `<localUid>` / `DOCUMENTID` | `DOCUMENTID` не применяется к ИЭМК |
| ID в РЭМД | `<emdrId>` | |
| OID организации | `<organization>` | → `dim_licenses.mo_uid` → JID |
| Код / название СЭМД | `<kind>`, `<name>` | Название также из `dim_semd_types` (НСИ `1.2.643.5.1.13.13.11.1520`) |
| Ошибка | `<code>`, `<message>`; при `LOGSTATE = 3` — `LOGTEXT` | Вход классификатора |
| Дата создания | `<creationDateTime>` | `safe_cast_timestamptz` |
| Номер протокола | `<documentNumber>` / `PROTOCOLID` | → `doc_number`; ключ группировки версий (см. §«Версии и идентичность документа») |

**Статус сообщения** (`classify_async_status`) — проекция одной строки журнала: `success`, `error`, `accepted`, `unknown`. `accepted` соответствует синхронному приёму запроса (шаг 4 схемы); на текущем контракте источника ветка зарезервирована (см. §«Контекст»). Регистрация приходит асинхронным callback с `registerDocumentResult` / `<documentStatus>Зарегистрировано</documentStatus>`. `LOGSTATE = 3` → `error` (транспорт). `pending` используется на уровне документа как состояние отправки.

**Статус документа** в `documents` — итог по цепочке сообщений одной подачи (4 канонических, `dim_document_status`):

| `status` | Метка | LOGID-якорь | MSGID-якорь |
| --- | --- | --- | --- |
| `sent` | **Отправлено**: файл запрошен РЭМД (`getDocumentFile`), есть связанная подача в `EGISZ_MESSAGES`, ответа ещё нет | `request_logid` | `msgid` |
| `network_error` | Ошибка связи | `result_logid` (LOGSTATE 3) | — |
| `async_error` | Ошибка асинхронного ответа РЭМД | `result_logid` | `msgid` / `relates_to_msgid` |
| `success` | Успешно зарегистрирован | `result_logid` | `msgid` / `relates_to_msgid` |

Транспорт СЭМД именуется по записям журнала: **запрос файла** (`getDocumentFile`, шаг 6) = `request_*`, **исход** (ответ РЭМД или сбой связи) = `result_*`. В витрине `logid = COALESCE(result_logid, request_logid)` — у отправленных без ответа это LOGID запроса файла.

Код нефинального статуса задан один раз в `dim_document_status` и читается функцией `document_status_nonfinal()`; ветви `transform_raw_to_facts` используют справочник.

**ЮЛ:** `resolve_document_jid(org_oid, endpoint)`. Основной источник — OID медорганизации из содержания обмена через `dim_organizations.fir_oid`; резервный источник — адрес обмена `gost-<N>` (`REPLY_TO` подачи = `MO_DOMEN` лицензии). `clinic_oid_unknown` означает отсутствие OID из обмена в реестре организаций.

## Связывание сообщений

Журнал шлюза содержит входящие вызовы ЕГИСЗ→шлюз. Исходящее сообщение, которым IPS подаёт документ (`registerDocument` в РЭМД, `ProvideAndRegisterDocumentSet-b` в ИЭМК), хранится в реестре подач. Асинхронный ответ содержит `relatesToMessage` / `relatesTo`, ссылающийся на подачу; связь ответа с документом строится через `dim_message_document`.

| Уровень | Ключ | Источник |
| ------- | ---- | -------- |
| Сообщение журнала | `logid` | `EXCHANGELOG` |
| Подача документа (попытка) | `msgid` | `EGISZ_MESSAGES` → `dim_message_document` |
| Экземпляр документа РЭМД | `dwh_id` = `lower(localUid)` | `DOCUMENTID` реестра либо payload запроса |
| Логический документ | `document_group_id` | `jid` + `semd_code` + `doc_number` |

`msgid → document_uid` однозначен; на один документ приходится несколько `msgid` — по одному на попытку подачи. Число подач хранится в `documents.attempt_count` и выводится на вкладке «Отправленные».

Правила привязки по классам сообщений:

| Класс сообщения | Ключ привязки |
| --------------- | ------------- |
| `getDocumentFile`, `LOGSTATE = 0` | `localUid` из payload + наличие `dim_message_document.document_uid` |
| `getDocumentFile`, `LOGSTATE = 3` (сбой связи) | `localUid` из конверта + наличие `dim_message_document.document_uid` |
| Ответ РЭМД (`sendRegisterDocumentResult`) | `relatesToMessage` → `message_registry_key` → `dim_message_document.document_uid` |
| Ответ ИЭМК (`ProvideAndRegisterDocumentSet-bAsyncResponse`) | `relatesToMessage` → `message_registry_key` → `dim_message_document.msgid`; `document_uid` не ожидается |
| Повторный или поздний ответ | `emdrId` → `documents.emdr_id` (подтверждающий путь) |

Применённое правило пишется в `transactions.link_method` (`payload_local_uid` / `message_registry` / `message_registry_no_document` / `emdr_id` / `unlinked`). `message_registry_no_document` — health-признак РЭМД: `relatesToMessage` найден в `EGISZ_MESSAGES`, `DOCUMENTID` пустой. ИЭМК в этот сигнал не входит. Ответы без записи в реестре получают метку `unlinked`; их доля выведена в `rpt_health_signals`.

Доля считается по последним 500 размеченным ответам **в порядке LOGID**. Окно следует порядку журнала независимо от времени приёма.

Ответ может создать запись в `documents` до события отправки: ЕГИСЗ отклоняет часть документов до запроса файла, и наблюдаемым событием остаётся сам ответ.

Окно разбора строго `(from_logid, to_logid]`: связывание опирается на строки текущего батча, поэтому отсечение партиций по `createdate` работает на каждом запуске.

## Сборка документа

Два слоя:

1. **Сообщение** — `transform_raw_to_facts` разбирает новые строки `exchangelog_raw` в `transactions` (поля `xml_*`, классификация ответа на уровне строки). Повторный разбор той же строки пропускается по маркеру `exchangelog_parse_attempts` (пишется на весь просканированный диапазон, включая отфильтрованные строки). Для строк `getDocumentFile` при разборе фиксируется `jid`: один вызов `resolve_document_jid` на строку за всю её жизнь вместо повторного разбора payload регулярным выражением на чтении.

2. **Экземпляр документа** — UPSERT в `documents` (PK `dwh_id` = `lower(localUid)`). Строки журнала одной отправки сходятся в одну запись по правилам из §«Связывание сообщений». Накапливаются `first_sent_at`, `last_callback_at`, `registered_at`, `attempt_count`, итоговый `status`, `error_types`, `jid`. Уровень записи — **версия отправки**: правка СЭМД меняет `localUid` и создаёт новый экземпляр (см. §«Версии и идентичность документа»).

3. **Группы версий** — `recompute_document_versions(dwh_ids)` пересчитывает `document_group_id`, цепочку `supersedes_*` и `is_current_version` для затронутого батча и его соседей по группе; вызывается в конце `transform_raw_to_facts`, полный пересчёт — в суточном обслуживании.

Разделение LOGID документа: `request_logid` — запрос файла (`getDocumentFile`), `result_logid` — исход (ответ или сбой связи). `msgid` — собственный MSGID текущего события документа; `relates_to_msgid` заполняется только из XML `relatesToMessage` / `relatesTo`.

`document_attributes` (1:1 к экземпляру): OID происхождения, host, endpoint, `egisz_subsystem` (последнее непустое значение по строкам документа), BI-маски; обновляется после transform и в суточном обслуживании.

### Учёт отправленных

`status = 'sent'` — файл запрошен РЭМД и подача подтверждена строкой `EGISZ_MESSAGES`, ответ ожидается. `getDocumentFile` без строки реестра остаётся транспортной диагностикой и не создаёт документ в состоянии отправки. Сценарии получения связанных ЭМД (`demandContent`, `getDocumentFileRequest` по `emdrId`, `sendDocumentFileRequest`) не входят в «Отправленные без ответа». В отчётном слое `sent` раскрывается **ступенью возраста обработки** и **состоянием отправки**.

**Лестница ступеней** — справочник `dim_pending_segments` (возраст от `first_sent_at`):

| Ступень | Граница | Состояние |
| ------- | ------- | --------- |
| до 5 минут · до 1 часа · до 6 часов · до 12 часов · до 24 часов · до 3 суток · до 7 суток | `max_age_minutes` | `pending` — **В обработке** |
| свыше 7 суток | терминальная (`NULL`) | `no_response` — **Без ответа** |

Точка перехода задаётся флагом `is_no_response` в справочнике. Ужесточение порога выполняется `UPDATE` по справочнику, без правки SQL и без пересчёта фактов. Отправки без известного `first_sent_at` попадают на терминальную ступень.

**Правило отображения:**

| Состояние | Цвет | Где учитывается |
| --------- | ---- | --------------- |
| **В обработке** (`pending`) | светло-синий | Наравне с исходами: распределения статусов, объёмы, динамика |
| **Без ответа** (`no_response`) | светло-серый | Только вкладка «Отправленные» |

`status_detail` — единое измерение из пяти значений (три исхода + два состояния отправки); карточки распределений отбирают по нему условием `status_detail <> 'no_response'`.

**Знаменатели долей.** «% успеха» и «% ошибок» считаются по корпусу с ответом:

```
доля успеха = success / (success + async_error + network_error)
```

`pending` — состояние ожидания; метрики отношения отбирают по `status <> 'sent'`. Распределения и счётчики объёма учитывают текущие состояния отправки.

В корпус с ответом входят документы, отклонённые ЕГИСЗ до запроса файла: для них наблюдаемым событием является ответ, который создаёт запись (см. §«Связывание сообщений»).

## Версии и идентичность документа

Журнал хранит SOAP-обёртку РЭМД; тело CDA (base64) находится вне контракта журнала. Парсер извлекает из обёртки `localUid`, `documentNumber`, `emdrId`, корреляционные MSGID. Поля CDA `setId` / `versionNumber` / `relatedDocument` в `MSGTEXT` отсутствуют.

| Уровень | Смысл | Источник в обёртке | Поле DWH |
| ------- | ----- | ------------------ | -------- |
| Экземпляр / версия | UUID конкретной выгрузки СЭМД; меняется при правке и ре-выгрузке | `localUid` | `dwh_id` (PK) |
| Логический документ | Цепочка версий одного документа в МИС | `jid` + `semd_code` + `doc_number` | `document_group_id` |

`doc_number` — номер протокола/ИБ (`PROTOCOLID` / тег `documentNumber`), подтягивается из `transactions` в `documents` на шаге группировки. Экземпляры без `documentNumber` остаются одиночными группами (`singleton`).

Логика `recompute_document_versions` (`db/03_transform.sql`):

| Условие | `document_group_id` | `document_group_confidence` | Группа версий |
| ------- | ------------------- | --------------------------- | ------------- |
| Нет `jid`, `semd_code` или `doc_number` | `dwh_id` | `singleton` | нет (экземпляр сам себе группа) |
| Ключ заполнен, в группе 1 экземпляр | `dwh_id` | `singleton` | нет |
| Ключ заполнен, 2…50 экземпляров (`c_cap`) | `grp_key` из `recompute_document_versions` | `doc_number` | да |
| Ключ заполнен, > 50 экземпляров | `dwh_id` | `singleton` | нет (защита от переиспользования счётчика протокола) |

В реальной группе: `semd_version_number` — порядок по `first_sent_at`; `is_current_version = true` ровно у одного экземпляра (`success`, иначе последнее IPS-событие); связь версий — `supersedes_dwh_id` / `superseded_by_dwh_id`.

Витрины: `rpt_documents` — только `is_current_version`; полный аудит — `rpt_document_versions`; контроль группировки — `rpt_health_versions` (размер групп, коллизии `localUid` по `transactions`).

## Классификация ошибок

РЭМД отдаёт ошибки как SOAP-faultcode, массив `<item>` (`code` + `message`), фрагменты Schematron; контур ИЭМК (IHE XDS.b) — атрибутами `<rs:RegistryError errorCode codeContext>`, которые `xml_registry_errors` приводит к тем же парам `code`/`message`. Правила — `dim_error_rules` (`db/02_functions.sql`); логика — `db/02_functions.sql`.

Основной справочник кодов и наименований ошибок — НСИ «РЭМД. Классификатор кодов сообщений» (OID `1.2.643.5.1.13.13.99.2.305`) в `dim_nsi_error_code` (`nsi_error_code` — мнемоника, `nsi_error_description` — описание справочника дословно). Правило, ссылающееся на код регистрационного пути, объявляет `code_namespace = 'НСИ 305'` и указывает `nsi_error_code`; внешний ключ контролирует наличие кода в справочнике. Два других пространства имён: `IHE XDS` (errorCode контура ИЭМК) и `шлюз` (`INTEGRATION_LOGSTATE_3` — сбой транспорта до РЭМД). Расхождения написания между ответом РЭМД и справочником (`RECIPIENT_*` против `RECEPIENT_*`) снимает `dim_nsi_error_code_alias`: синоним разрешается до сопоставления, правило заводится на каноничную мнемонику.

Текстовое правило (ярус 3–4) наследует зонтичную мнемонику регистрационного пути через `parent_nsi_error_code`: `RUNTIME_ERROR` для технических отказов РЭМД, `VALIDATION_ERROR` для остальных проверок контура регистрации, `NULL` для ИЭМК и шлюза, чьи коды лежат вне НСИ 305. Отчётный слой показывает код отказа как `COALESCE(nsi_error_code, parent_nsi_error_code)`, поэтому у типа, распознанного по формулировке, в отчёте стоит зонтичная мнемоника.

Для контуров ИЭМК и шлюза `dim_error_type_group` хранит пару `code_namespace` + `error_code` — код в своём справочнике (`НСИ 305`, `IHE XDS`, `шлюз`). Витрина `rpt_error_breakdown` отдаёт эту пару рядом с мнемоникой, а разбор «Ошибки: тип × клиника» показывает колонками «Код отказа» и «Справочник». Код проставляется для типов с единственным кодом; многокодовые трактовки остаются на уровне категории и наименования типа.

Матчинг **ярусный** (`match_tier`): на каждый `<item>` правила проверяются по возрастанию яруса, и первый ярус с совпадением закрывает поиск для этого item. Семантика ярусов: **1** — код + специфичный текстовый паттерн; **2** — только код (`match_pattern = '(?is).*'`, пустой `message` допустим); **3** — специфичный текстовый паттерн без кода; **4** — широкие текстовые фолбэки. Ярус 2 покрывает классификатор ФНСИ за исключением зонтичных кодов `VALIDATION_ERROR` и `RUNTIME_ERROR`, для которых диагностика берётся из текстовых ярусов. Уточняющие правила ярусов 1 и 3 построены по методической документации «Описание выполняемых проверок в РЭМД»: кросс-валидация запроса и СЭМД (§5.2–5.5), валидация даты и последовательности подписей (§4.8–4.9), классы ошибок схематрона (§5.8 — указание отсутствия информации, связанный документ, адрес), валидация по XSD (§5.7).

Несколько совпадений внутри выигравшего яруса дедуплицируются; мультитиповость документа возникает из нескольких `<item>` или нескольких совпадений одного яруса. Для отказа без правила показывается нормализованная формулировка `remd_error_type()`: значения в скобках, OID, идентификаторы, номер правила схематрона и хвост `Путь: /ClinicalDocument…` удаляются. Остаток «Код: X» используется для кода вне классификатора и без текста; по нему строится контрольный сигнал «Отказы без правила классификации». Все типы контура ИЭМК начинаются с префикса `ИЭМК: `.

**Подсистема ЕГИСЗ** (`transactions.egisz_subsystem`: `РЭМД`/`ИЭМК`/NULL) вычисляется `egisz_subsystem()` первично по `URI` вызова (`/emdr/callback` → РЭМД, `/ips/callback` → ИЭМК). Это реквизит транспорта, заполненный до разбора payload во всех строках, включая сбои связи без тела ответа. Запасные признаки для строк без `URI` — `wsa:Action` (`urn:ihe:*` → ИЭМК, иной непустой → РЭМД) и порт сервиса клиники в `LOGTEXT` (`:9921` → ИЭМК, `:9945` → РЭМД). На уровне документа значение фиксируется в `document_attributes.egisz_subsystem` (последнее непустое по строкам документа) и оттуда экспонируется в `rpt_network_errors.egisz_subsystem`.

Связь **тип → группа** хранится в центральном справочнике `dim_error_type_group` (тип PK → категория). Уникальный ключ типа задаёт одну группу для каждого типа. Каждый тип дополнительно несёт `responsibility` (кто устраняет причину: клиника / МИС / интегратор / РЭМД / смешанная) и `is_retryable` (лечится ли повторной отправкой) — см. [приложение](#зона-ответственности-и-повторяемость).

В `documents`:

| Поле | Содержание |
| ---- | ---------- |
| `error_types` | Канонические **типы** документа (один или несколько) через `·`; в БД хранится полным списком |
| `error_text` | Исходный текст из `<message>` **без редактирования** |

`rpt_error_breakdown` раскладывает `error_types` на атомарные строки (split по `·`): 1 ряд = 1 канонический тип на документ (поле `error_type`); категория, зона ответственности и повторяемость подтягиваются JOIN'ом к `dim_error_type_group`.

Перечень типов — [приложение](#приложение-типы-ошибок). Условия правил — [справочник](#справочник-активных-правил-классификации).

| `loaded_at` (`transactions`) | Момент загрузки строки журнала в ELT | Служебное поле слоя транзакций |

День периода берётся из полной даты инлайн (`ips_date::date`), без `AT TIME ZONE` — стек пиннится МСК (`report-timezone=Europe/Moscow`).

## Приложение: типы ошибок

Классификатор сопоставляет `code` и текст `<message>` из callback с правилами DWH (ярусный матчинг — см. §«Классификация ошибок»). Несколько типов в одном документе разделяются `·`.

Наименования типов — формулировки справочника НСИ «РЭМД. Классификатор кодов сообщений» (OID `1.2.643.5.1.13.13.99.2.305`, версия 3.18): все 127 мнемоник заведены в `dim_nsi_error_code`; правило яруса 2 задано для мнемоник с самостоятельной диагностикой. Для зонтичных `VALIDATION_ERROR` и `RUNTIME_ERROR` причина определяется текстовыми правилами, а код ответа сохраняется в `parent_nsi_error_code`.

Контур ИЭМК покрыт своим пространством имён: живые платформенные коды (`XDS.CDA.*`, `XDSDictionaryValidationError` и др.) плюс стандартные коды IHE ITI TF-3 регистрационного пути ITI-41/42; внутренние коды платформы (`CRE-NNN`, `PAT-NNN`) приходят в `codeContext`. Отказ без правила классификации показывается собственной формулировкой РЭМД — см. §«Классификация ошибок».

### Зона ответственности и повторяемость

Каждый тип в `dim_error_type_group` несёт `responsibility` (кто устраняет причину: `клиника` / `МИС` / `интегратор` / `РЭМД` / `смешанная`) и `is_retryable` (устраняется ли повторной отправкой без правки данных). Обе колонки экспонируются в `rpt_error_breakdown`. Значения по умолчанию — по категории:
