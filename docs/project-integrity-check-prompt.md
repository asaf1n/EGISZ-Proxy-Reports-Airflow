## Ограничения

- **Прод.** Ничего не применять без явного «да» пользователя. По каждому действию на проде — блоки «через API» и «вручную».
- **Прод DWH** — только чтение: `default_transaction_read_only=on`, `search_path=public`.
- **Прод Metabase** (`bi.sdsys.ru`, коллекция 37, подключение к DWH id 34) — только GET с заголовком `x-api-key`. Выгрузка — только `scripts/export_dashboard.py --backup`: запуск без ключа перезаписывает `metabase_dashboards/`. Не доступен на данный момент.
- **Прод Airflow** (`airflow.sdsys.ru`) — только чтение через REST API. DAG-файлы выкладывает пользователь. Не доступен на данный момент.
- **Локальный контур.** Запуск и пауза DAG-ов — после подтверждения пользователя. Пароль роли `postgres` не подбирать: локальный Metabase подключается к DWH учёткой из `k8s/metabase/metabase-connections-secret.yaml` (файл вне git).
- **Кириллица в SQL** — только файлом через `psql -f`: `psql -c` на Windows портит UTF-8.
- **Тесты с живой базой** — без параллельной нагрузки на неё: обновление витрин ловит `DeadlockDetected`.
- Персональные данные в ответ не выводить: только количества и замаскированные формы. Разовые скрипты — во временной папке, не в репозитории.

## 2. Локальное тестирование в Kubernetes

1. `kubectl config current-context` — `docker-desktop`; `kubectl get nodes` — узел `Ready`.
2. Если Airflow уже развёрнут — поставить DAG-и на паузу (с подтверждения).
3. Применить схему к локальной DWH дважды и сравнить снимок справочников.
4. `.\up.ps1` (или по частям `-Action Airflow`, `-Action Metabase`): сборка образов, развёртывание, импорт дашбордов, проверочные скрипты. Записать длительность шагов и ошибки.
5. Airflow (`http://localhost:8080`): DAG-и разбираются без ошибок импорта. После подтверждения — снять паузу, прогнать `egisz_etl_dag`: все задачи зелёные, `refresh_marts` обновляет шесть витрин. Один раз запустить `egisz_maintenance_dag` с параметром `reclassify_errors`: при неизменных правилах пересчёт ничего не меняет.
6. Metabase (`http://localhost:3000`): `verify_metabase_integration.py`, `verify_metabase_cards.py`. Затем карточки с реальными значениями фильтров через дашбордовую точку (`/api/dashboard/:id/dashcard/:dcid/card/:cid/query`): период, `clinic_label`, подпись СЭМД, тип ошибки; для клиентского дашборда — JID и категория ошибки. Посмотреть изменённые карточки: «РЭМД vs связь» и её переход, «Ошибки: тип × клиника» и переход в «Разбивку ошибок», карточки ошибок связи, клиентские вкладки.
7. `pytest` на спокойной базе.
8. Итог — таблица «шаг → результат → время».

## 3. Оставшиеся вопросы

### 3.1. Выкладка модели ошибок на прод

Порядок важен: карточки ошибок связи читают новые столбцы представлений.

1. Поставить DAG-и на паузу. Применить схему DWH из рабочей копии (`deploy/apply-dwh-schema.ps1`) дважды: второй прогон не должен менять содержимое справочников. Проверить столбцы `network_error` и `message_error`.
2. Выложить `dags/egisz_etl_dag.py` и `dags/egisz_maintenance_dag.py`, если на проде ещё прежние: прежний DAG обновляет снятые витрины и падает на `refresh_marts`. Снять паузу, дождаться зелёного прогона.
3. Проверить, что подключение Metabase к DWH (id 34) синхронизирует схемы `stg_egisz`, `mart_egisz`, `mart_egisz_selfservice` (`details.schema-filters-type`, `schema-filters-patterns`). Иначе импорт остановится на ожидании метаданных. 27.09.2026 `bi.sdsys.ru` отвечал 403 даже на `/api/health`, хотя DWH прода был доступен, — выяснить причину до импорта.
4. Проверить права роли, под которой Metabase читает DWH: `USAGE` на три схемы и `SELECT` на объекты карточек, включая `stg_egisz.document_error_current` и `stg_egisz.message_error`.
5. Снять снимок коллекции (`scripts/export_dashboard.py --backup`), затем импорт (`deploy/import-metabase.ps1`). Переименованные карточки («Типы сетевых ошибок (за период)» → «Типы ошибок связи (за период)», «Топ типов СЭМД по видам ошибки» → «Топ типов СЭМД по типам ошибок») архивируются по `metabase/retired-objects.json`.
6. После импорта — `scripts/verify_metabase_cards.py` и карточки с параметрами. Проверить, что живой дашборд совпадает с репозиторием: раньше на нём оставались снятые карточки.
7. Проверить карточки 694 и 695: их списки полей раньше выводили тексты с персональными данными.

Отдельно ответить:

- **XmR и фазы.** Определение доли ошибок изменилось, история пересчитана по новому определению целиком, опорный период фазы задан датами. Нужна ли новая фаза в `dim_control_chart_phases` или смена определения не является сменой условий работы?
- **Переход в «Разбивку ошибок».** Модель содержит все текущие ошибки документа, в том числе элементы успешных ответов; карточки считают только область разбора.
