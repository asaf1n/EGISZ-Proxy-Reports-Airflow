## Цель и границы

Выполни локальные исправления ошибочного отчёта о тайм-аутах и медленных дневных
карточек очереди, заверши относящуюся к ним проверку ошибок. Отдельно подготовь
решение для перехода всех потребителей на чтение только `serving_egisz`:
сначала Metabase, в дальнейшем Superset и ИИ. По этому переходу выполняется
только оценка: не создавай новые объекты выдачи, не переноси источники карточек
и не меняй структуру хранения, закреплённую в плане раскладки.

Код разрешено менять только для исправления проверки, двух дневных запросов,
их проверок и необходимых описаний. Живой Metabase — только чтение метаданных
и выполнение запросов карточек; не импортировать, не синхронизировать и не
изменять карточки, модели, подключения и разрешения. Прод не изменять.
Роли DWH, права, фильтр схем Metabase, подключение Superset и ИИ — отдельные задачи.
Не делать коммит и push. Сохранять существующие изменения пользователя.

Различай результат SQL из репозитория и результат уже импортированной карточки.
Если их версии расходятся, покажи это явно. Не называй изменённый SQL проверенным
через Metabase до его отдельного разрешённого импорта.

## 2. Исправить учёт ошибок отдельных карточек

В `scripts/verify_metabase_cards.py` функция `verify_card_query()` перехватывает
`HTTPError`, но не `TimeoutError` и не остальные `URLError`. Исключение выходит
через `future.result()` и ошибочно получает подпись `health/login failed`.

Перехватывай тайм-аут внутри проверки конкретной карточки и возвращай сообщение
с дашбордом, названием/идентификатором карточки и фактическим лимитом, например
`<dash> / <card>: query exceeded 45 s`. `URLError` с причиной тайм-аута обрабатывай
так же; прочие сетевые ошибки называй ошибками соединения конкретной карточки,
не выдавай их за превышение времени. Сохрани более узкую обработку `HTTPError`
перед `URLError`. Ошибка `login()` остаётся фатальной. Не увеличивай лимит 45 с
в качестве исправления и не подавляй все исключения общим `except Exception`.
Учти `_urlopen_retry` в `scripts/mb_api.py`: сетевой вызов может повторяться до
четырёх раз. 45 с — лимит отдельной попытки, а не гарантированный предел полного
задания. Не меняй глобальную политику повторов попутно и не представляй этот
лимит как измеренную полную длительность запроса.

Добавь тест с подменённым `api_json`: одна карточка выдаёт `TimeoutError`, другая
возвращает отдельную ошибку запроса, третья успешно завершается. Докажи, что
сбор результатов через `verify_cards()` продолжается, обе ошибки попадают в
итог, успешное задание выполнено, сообщения об ошибке входа нет. Дополнительно
проверь `URLError` с причиной тайм-аута, другой `URLError`, сохранение обработки
HTTP и фатальность отказа входа. Размести проверки в `tests/` по стилю проекта.

Для незавершённой проверки привязок добавь явный режим с реальными параметрами
через `/api/dashboard/:id/dashcard/:dcid/card/:cid/query`. Сейчас
`build_query_parameters()` передаёт только обязательный `client_jid`.
Используй действительные значения периода, `clinic_label`, `semd_label`, типа
ошибки; для клиентских карточек — JID и категорию. Для очереди — ступень на
момент соответствующей точки ряда. Проверяй только поддерживаемые карточкой
параметры. Отсутствующие данные помечай как непроверенный случай, а не успех.
Сохрани обычный режим; добавь проверки формирования параметров и продолжения
сбора ошибок в новом режиме. Не выводи исходные тексты и персональные данные.

## 3. Ускорить оставшиеся карточки очереди

Исследуй `QUEUE_TREND_CORPUS`, `QUEUE_TREND_POINT_QUEUE`, `QUEUE_SIZE_QUERY`,
`QUEUE_OVER_24H_QUERY` и `QUEUE_TAIL_QUERY` в `scripts/apply_dashboard_plan.py`.
Проверь участие `scripts/layout_operational_tab.py`; генераторы обслуживаются
парой. Две дневные карточки размещены на вкладках `sent` и `operational`:

- «Документов в очереди (без фильтра периода)»;
- «Ожидают > 24 часов (без фильтра периода)».

Используй приём существующего `QUEUE_TAIL_QUERY`: диапазонный отбор по
`first_sent_at`, ограничение кандидатов по порогам справочника и развёрнутый
предикат отсутствия ответа на момент точки. Сохрани `pending_segment` с его
историческим смыслом; не заменяй его текущей ступенью документа. Сохрани пустые
точки, `COUNT(DISTINCT dwh_id)`, NULL, точные включения границ, порог «старше
24 часов», временную зону, неполный текущий день и остальные действующие фильтры.
Пороги не зашивать в код. Не менять доменную семантику функций ради скорости.

Повторно измерь «Доля долгого ожидания по неделям (без фильтра периода)».
Если текущий SQL уже укладывается в лимит и эквивалентен, оставь его. Если
медленным оказался старый SQL живой карточки, зафиксируй необходимость импорта,
но сам импорт не выполняй. Значения 133 с и 0,78 с из предыдущего обсуждения
не считай новыми измерениями.

Локальная DWH: `localhost:5432`, база `dwh_egisz`, пользователь `egisz`, пароль
локального контура `egisz`. Передавай реквизиты через штатные параметры запуска,
не добавляй их в производственный код. SQL с кириллицей выполняй UTF-8-файлом
через `psql -X -v ON_ERROR_STOP=1 -f`, не через `-c`.

Старый и новый SQL сравни в одной транзакции `REPEATABLE READ` с единым моментом
расчёта. Проверяй `EXCEPT ALL` в обе стороны для полного набора строк, отдельно
структуру и порядок результата. Сравни без необязательных фильтров, с реальной
клиникой/СЭМД, каждой применимой ступенью и граничными значениями времени.
Сними `EXPLAIN (ANALYZE, BUFFERS)`, время и план доступа к
`idx_documents_first_sent_at`. Не принуждай PostgreSQL к индексу настройками
планировщика. Длительный эталонный запрос допускается выполнить с отдельным
локальным лимитом для сверки; штатный лимит проверки карточек не повышать.

## 4. Оценить переход потребителей на serving_egisz

Источники: `metabase_dashboards/*.json`, `metabase_models/*.json`, оба генератора,
`metabase/setup-dashboards.sh`, `metabase/sync-models.sh`,
`scripts/verify_metabase_cards.py`, определения SQL. Живой Metabase читать
только для сопоставления фактического состояния с репозиторием.

Подготовь полную матрицу «карточка/модель и вкладка → текущий источник → объект
serving_egisz → изменение → проверка». Учитывай SQL, привязки полей, модели и
переходы. Каждое размещение карточки учитывай отдельно. Отличай прямую ссылку
потребителя от внутренних зависимостей существующего представления.

Оцени выдачу двух справочников как `pending_segments` и `control_chart_phases`.
Для `documents` и `exchange_messages` сначала докажи нехватку существующих
`documents_current`, `document_versions`, `documents_sent`, `network_errors`
и `document_file_requests`; не создавай полную выдачу базовых таблиц без потребности.

Для чтений `stg_egisz.document_errors_current` и `stg_egisz.message_errors`
сопоставь отказ от исходного текста с выдачей проверенного обезличенного поля.
Рекомендуемый исходный вариант — существующие тип, код, время и идентификаторы.
Проверь также колонку «Сообщение» в
`mart_egisz_admin.health_message_registry_no_document`: в ней `tx.message`.
Обрезка текста не заменяет обезличивание. Сохраняй исходные данные в разборе;
не переопределяй `error_type` и не смешивай ошибку связи со статусом регистрации.

Эксплуатационные определения оставь в `mart_egisz_admin`. Если их карточки
остаются в Metabase, предложи ограниченную выдачу нужных полей через serving,
сохранив ключ и детализацию. Не публикуй все `health_*` автоматически.

Для каждого нового объекта опиши назначение, детализацию строки, ключ, явный

список — пять объектов из оценки; окончательный состав обоснуй потребителями.

Покажи риски смены идентификаторов полей Metabase: `table_ref`,
`template-tags.dimension`, `parameter_mappings`, поля моделей, переходы и полные
квалификаторы в field filters. `DWH_SCHEMAS_REGEX` — механизм поиска зависимостей
для проверки импорта, а не ограничение доступа. Не сужай его, скрывая нарушения.

## 5. Завершить относящиеся к задаче проверки

Запусти пару `apply_dashboard_plan.py` → `layout_operational_tab.py` дважды.
После первого запуска ожидается только обусловленное исправлением изменение
JSON; второй не должен добавлять изменений. Сравни файлы/хеши между прогонами:
наличие ожидаемого diff относительно HEAD не является нарушением идемпотентности.
JSON вручную не редактировать. Синхронно обнови затронутые проверки и описания.

В PowerShell задай `$env:EGISZ_TEST_PG_DSN` значением
`postgresql://egisz:egisz@localhost:5432/dwh_egisz`, затем выполни
`python -m pytest -q` в переднем плане. Параллельной нагрузки на DWH не создавать.
Проверь состояние локальных DAG и выполняющихся запросов до тестов. Разрешение
на временную паузу и локальные прогоны уже дано в прежней сессии; при необходимости
используй его и верни зафиксированное перед работой состояние. Не запускай
повторный пересчёт и развёртывание без необходимости. Не откатывай курсоры.

Проверь все доступные карточки живого Metabase с исправленным скриптом, затем
значения фильтров и переходы. Сопоставь область карточек ошибок с моделью

нельзя заменить только статусом отказа. Различай число элементов ошибок и
число `DISTINCT dwh_id`. Прежние 1117 элементов по 660 документам перепроверь;
изменение области модели или переходов пока только предложи.

Сохрани ограничения прежней проверки: штатные пропуски задач DAG не являются
сбоем, но не подтверждают ветви с новыми данными; прежние 403 и замеры не
подтверждают текущее состояние прода. Остальные рекомендации старого отчёта
перечисли как отдельные незавершённые пункты, не реализуй их попутно.
